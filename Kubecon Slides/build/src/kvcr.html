Distributed KV Cache Management with Dynamo Router and KVCR

  • Distributed KV cache management with the Dynamo Router and KVCR (KV Cache Runner).
  • The idea in one line: the router plans where KV should be, and KVCR moves it between workers.
The problem

Four requirements for KV cache management

1

Avoid recompute

Store KV in cheaper tiers and bring it back instead of recomputing.

2

Avoid hot spots

One popular prefix shouldn't pin all its traffic to one worker.

3

Recover failures

Losing a worker shouldn't mean recomputing its whole cache.

4

Signal aware

The workload knows when KV is done with — use that signal.

  • Store and retrieve, avoid hot spots, assume failures, take input from the workload.
  • 1. Avoid recompute: offload KV down the tiers (HBM → DRAM → remote storage) and retrieve it instead of recomputing.
  • 2. Avoid hot spots: many requests with the same prefix pile onto the one worker that holds it while others sit idle.
  • 3. Recover failures: when a worker dies its cache is lost and another worker has to recompute it.
  • 4. Signal aware: the agent harness knows when a sub-agent finished or a context was compacted, which tells us that KV is safe to evict.
Dynamo’s approach

Router plans. KVCR acts.

  • Others: the router is load and KV aware, but a separate KV cache manager decides on its own where KV goes.
  • Dynamo + KVCR: 1) the router is hint-aware — it takes signals from the client; 2) it plans KV moves and sends them as hints that ride on requests; 3) the KVCR library inside each worker carries them out, moving KV between workers.

KVCR-Guard · try it

Recovering from failures

The DRAM pool sits in its own container, KVCR-Guard, so it can outlive the engine. The engine fails and G1 is lost. The pool survives. The guard confirms the engine is dead — a timeout alone isn’t enough to take over. The backup serves the pool. Worker A copies the KV from B’s pool, peer to peer, instead of recomputing it. The engine comes back and refills G1 from the pool — a copy, not a recompute — then a fenced handoff returns control.
  • The pool sits in its own container (KVCR-Guard), so it can outlive the engine. A backup KVCR waits on standby.
  • Engine fails: B’s G1 is lost but the G2 pool survives. The guard confirms the engine is dead before taking over; a timeout alone is not enough.
  • Backup serves the pool: the router sends t2 to Worker A with a hint to fetch from B’s pool; the backup KVCR serves it peer to peer.
  • Engine returns: it refills G1 from the pool (a copy, not a recompute), and there is a fenced handoff back to the engine.
