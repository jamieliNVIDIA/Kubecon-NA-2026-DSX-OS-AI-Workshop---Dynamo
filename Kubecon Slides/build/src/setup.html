# terminal 1 · frontend on :8000
python3 -m dynamo.frontend --discovery-backend file

# terminal 2 · a worker (pick your engine)
python3 -m dynamo.vllm --model Qwen/Qwen3-0.6B \
    --discovery-backend file
#   dynamo.sglang / dynamo.trtllm take --model-path

# terminal 3 · ask it something
curl -sf localhost:8000/health && echo OK
curl localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"Qwen/Qwen3-0.6B",
       "messages":[{"role":"user","content":"Hello!"}],
       "max_tokens":50}'

        
Press → to start the worker, then send a request.

      

    

  

  
  • From the Local Guide quickstart. The frontend serves the OpenAI-compatible API on port 8000; the worker registers through file discovery and the frontend finds it.
  • The deployment guide variant uses etcd + NATS and adds demo flags --enforce-eager --max-model-len 4096 for vLLM.






  
Local · scale the shape
Launch presets: from one worker to disaggregated with a KV router

    

  

    

      

      

        
quickstart · 1 GPU
One aggregated worker does prefill and decode. Fine for a smoke test and small models.

        
launch/agg_router.sh · 2 GPUs
Two workers behind the KV-aware router: requests go to the worker that already holds the prefix. vLLM needs PYTHONHASHSEED=0 for matching block hashes.
TRT-LLM preset: 1 worker.

        
launch/disagg.sh · 2 GPUs
1 prefill + 1 decode worker. KV moves prefill → decode over NIXL. Workers take --disaggregation-mode prefill|decode; vLLM needs a unique VLLM_NIXL_SIDE_CHANNEL_PORT per worker.

        
launch/disagg_router.sh · 4 GPUs
2 prefill + 2 decode with the KV router picking the prefill worker. TRT-LLM preset: 1P + 1D on 2 GPUs.


# presets live per backend
cd examples/backends/vllm   # or sglang, trtllm
./launch/disagg_router.sh

      

    

  

  
  • Presets from examples/backends/{vllm,sglang,trtllm}/launch/, described in the Local Guide's disaggregated-serving and KV-aware-routing pages.
  • GPU counts: agg_router 2 (vLLM/SGLang) or 1 (TRT-LLM); disagg 2; disagg_router 4 (vLLM/SGLang) or 2 (TRT-LLM).
  • The old --is-prefill-worker flag was removed in v1.4.0; use --disaggregation-mode.

I need

      

      

      
Pick what you need to see which add-on it brings in, and why.

    

  

  
  • From the Kubernetes quickstart and install guide. Add --set driver.enabled=false to the GPU Operator install when the cloud provider manages drivers. $CHARTS is https://helm.ngc.nvidia.com/nvidia/ai-dynamo/charts. Prerequisites: Kubernetes ≥1.30 with GPU nodes, kubectl ≥1.30, Helm v3+. Verify: CRDs present, dynamo-operator-* and nats-* pods running.
  • Add-ons: multinode needs Grove + KAI Scheduler or LWS + Volcano (the operator errors without one); production disaggregation needs RDMA via the Network Operator (TCP fallback: ~98 s TTFT vs ~200–500 ms with RDMA, per the install guide); Planner sla mode and KEDA/HPA need kube-prometheus-stack; models over 70B benefit from an RWX PVC model cache.
  • Docs caveat: the install guide still pins RELEASE_VERSION=1.2.1 while the quickstart uses 1.6.0. Use the current release.






  
Kubernetes · DynamoGraphDeployment
One DGD describes the whole serving graph

  

    

      

        
Backend


apiVersion: nvidia.com/v1beta1
kind: DynamoGraphDeployment
metadata: {name: qwen3-32b-agg}
spec:
  components:
  - name: Frontend
    type: frontend
  - name: worker
    type: worker
    replicas: 1
    podTemplate:
      spec:
        containers:
        - name: main
          image: nvcr.io/nvidia/ai-dynamo/vllm-runtime:1.6.0
          envFrom: [{secretRef: {name: hf-token-secret}}]
          command: [python3, -m, dynamo.vllm]
          args: [--model, Qwen/Qwen3-32B, --tensor-parallel-size, "2"]
          resources: {limits: {nvidia.com/gpu: "2"}}

      

      

        

        
GPU limit = TP × PPcontainer must be named mainTP inside a node · PP + multinode.nodeCount across

        
Hover the YAML to see what each part creates.

      

    

  

  
  • From "Deploy with DGD". API nvidia.com/v1beta1: spec.components is a list with name, type (frontend, worker, prefill, decode), replicas, multinode.nodeCount, sharedMemorySize and a podTemplate whose container is named main. The older v1alpha1 services map is still served and converted.
  • Backends: vLLM uses --model and CLI parallelism flags; SGLang uses --model-path and --tp; TRT-LLM takes parallelism in an engine YAML via --extra-engine-args.
  • Apply: envsubst < dgd.yaml | kubectl apply -f - (try --dry-run=server first), then kubectl wait --for=condition=Ready dynamographdeployment/<name>. Common rejections: GPU limit not TP×PP, multinode without Grove or LWS, missing secret.






  
Kubernetes · auto-deploy
Not sure how to size it? Ask for an SLA and let the profiler pick

  

    

      


apiVersion: nvidia.com/v1beta1
kind: DynamoGraphDeploymentRequest
metadata: {name: qwen3-quickstart}
spec:
  model: Qwen/Qwen3-0.6B   # the only required field
  backend: auto
  searchStrategy: rapid     # or thorough
  workload: {isl: 4000, osl: 1000}
  sla: {ttft: 2000, itl: 30}  # ms
  autoApply: true

        
rapid~30 ssimulated with AISim · no GPUs
thorough2–4 hreal GPUs + AIPerf · disagg only

      

      

        


# review before deploying: set autoApply: false, then
kubectl get dgdr my-model -o jsonpath=\
  '{.status.profilingResults.selectedConfig}' > my-dgd.yaml

      

    

  

  
  • From "Auto-deploy with DGDR" and the Profiler page. Phases: Pending → Profiling → Ready → Deploying → Deployed (or Failed; profiling failures are terminal).
  • Defaults: isl 4000, osl 1000, ttft 2000 ms, itl 30 ms. e2eLatency can replace ttft/itl. hardware.gpuSku / totalGpus / numGpusPerNode; modelCache for a PVC; features.planner to add the Planner.
  • The profiler optimizes for: independent prefill and decode engines when the Planner is on; the fewest GPUs that meet a target load when one is set; otherwise maximum throughput. MoE is fully supported on SGLang.
  • Deleting the DGDR does not delete the DGD it made.

Lever · KV-aware routing
Route each request to the worker that is cheapest to finish it

  

    

      


# frontend: turn it on (default round-robin)
--router-mode kv
# vLLM worker: publish KV events
--kv-events-config '{"publisher":"zmq",
  "endpoint":"tcp://*:20080",
  "enable_kv_cache_events":true}'
# tune through a policy file
--router-policy-config worker-selection.yaml

        
overlap_score_creditLower → spread load, lower ITL

        
prefill_load_scaleRaise → when long prompts saturate workers

      

      

        
Score by

        
cachedto computealready queued· an 8-block prompt arrives

        

        
overlap_score_credit1.0

        

      

    

  

  
  • Inspired by the router deck's "How it picks a worker". Each worker's cost = blocks it still has to compute + work it already has; lowest wins. Cache only piles onto the busy worker; load only throws away reuse; round-robin ignores both.
  • The real cost function (router configuration and tuning): prefill_load_scale × adjusted prefill blocks + decode blocks (+ optional active-request term). overlap_score_credit scales how much a cached block counts: lower it to spread load and reduce ITL; raise prefill_load_scale when long prompts saturate workers. router_temperature adds randomness.
  • Other flags: --no-router-kv-events (approximate routing), --router-predicted-ttl-secs 5 for fan-out or best-of-N bursts, --no-router-assume-kv-reuse for disagg, --router-queue-threshold and --router-queue-policy wspt|fcfs. The older --router-kv-overlap-score-credit and --router-prefill-load-scale flags are deprecated (removal in v1.7).
  • Worker numbers are a toy example. Deep dive: router.html.

✅ Use it for
  • Long prompts
  • High concurrency

  • When to use it (disaggregated serving overview): long prompts, high concurrency, or different TP needs per phase. When not to: small models, short prompts, or no fast fabric. Without RDMA, KV transfer falls back to TCP (the install guide quotes ~98 s TTFT vs ~200–500 ms with RDMA).
  • Live toy simulation: requests arrive (6/s), wait for a prefill worker (0.25 s each), hand their KV to the least-loaded decode worker, then stream 60 tokens; a decode step takes 20 ms + 2.5 ms per active stream on that worker. A request counts toward goodput if TTFT ≤ 1 s and its average ITL ≤ 35 ms. Start at 1P/2D: prefill can only do 4 req/s, so the queue grows and TTFT fails. Add prefill → TTFT recovers but decode streams pile up → ITL fails. Add decode → both pass. Keep adding → goodput per GPU drops. The ★ best split is found by a quick seeded sweep of all 36 splits when the slide loads (2P/3D with these settings). Real numbers: AISim or a DGDR profile.
  • Transfer-path check: the dynamo-interconnect-check agent skill ships scripts/check_interconnect.py with three read-only subcommands: env (NIXL/UCX/NCCL env vars on a recipe), node (InfiniBand, GPUDirect RDMA, GDRCopy, NVLink on a node or pod) and nixl (NIXL transfer-test readiness for a pod). Run it after deploying a disaggregated recipe.
  • Flags: --disaggregation-mode prefill|decode; sharedMemorySize: 16Gi in the DGD (64 MB default breaks NIXL); kubectl logs <prefill-pod> | grep NIXL should show UCX.
  • Project it first with AISim: aisimulate recommend searches parallelism, batching, replicas and agg vs disagg and returns the fewest GPUs that meet the SLA, in about 30 seconds without GPUs. The Kubernetes equivalent is a DGDR with searchStrategy: rapid.
  • Sizing once deployed: no fixed ratio; prefill queue grows → add prefill; decode KV near its limit → add decode; disagg worse than agg → check NIXL/RDMA first. vLLM flags: --kv-transfer-config with NixlConnector, kv_role kv_producer / kv_consumer.

Planner · in the DGDR


features:
  planner:
    mode: disagg
    optimization_target: sla  # default: throughput
    ttft_ms: 500.0
    itl_ms: 50.0
    enable_throughput_scaling: true  # every 180 s
    enable_load_scaling: true        # every 5 s
    advisory: true   # recommend only

        
step 1advisorywatch its recommendations
step 2throughputlet it scale
step 3sla+ Prometheus, both scalers

      

    

  

  
  • KV offloading backends are alternatives, not layers. LMCache via the vLLM KV connector; SGLang HiCache flags; FlexKV is experimental; KVCR is a separate, early-stage cross-node cache.
  • Planner is configured only through a DGDR (features.planner), not in the DGD. Guardrails: min_endpoint, prefill_min_endpoint, decode_min_endpoint, max_gpu_budget. Only sla mode needs Prometheus. Scale-down does not drain in-flight requests.
  • Advisory mode emits dynamo_planner_predicted_num_{prefill,decode}_replicas without acting.
