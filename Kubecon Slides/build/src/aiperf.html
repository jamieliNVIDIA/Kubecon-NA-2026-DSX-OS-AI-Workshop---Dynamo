AIPerf

Benchmark any inference endpoint with production-shaped traffic, and get the metrics that decide your SLA.

pip install aiperfApache 2.0successor to GenAI-Perf
  • AIPerf (github.com/ai-dynamo/aiperf) is a benchmarking tool that measures the performance of generative AI models served by any inference solution. It is a ground-up rewrite and successor to GenAI-Perf (NVIDIA developer blog, Sep 2026); docs/migrating.md calls it a drop-in replacement for currently supported features.
  • Latest release v0.13.0 (Sep 24 2026): native Kubernetes execution (beta), speculative-decoding metrics, richer workload control.

Architecture

Three planes, so measuring never gets in the way of sending

~10 services in separate processes, talking over ZMQ. Press → to follow one request.

① Credit. The Timing Manager sends a credit, permission to send exactly one request, to a worker.

② Data. The worker reads its prompt from memory-mapped dataset files. No copies, no waiting.

③ Request. The worker sends it to your server and timestamps every streamed chunk.

④ Return. The credit goes back to the Timing Manager. A slow server means fewer free credits: natural backpressure.

⑤ Records. Raw results go to Record Processors, which scale with load and compute per-request metrics.

⑥ Results. The Records Manager aggregates and exports, alongside GPU and server metrics.

ZMQ pub/sub + ROUTER/DEALERwarm-up discardedsingle node or Kubernetes
  • From docs/architecture.md. Control plane: SystemController, Timing Manager, Dataset Manager, Worker Manager ("decides what, when, and how many requests to send"). Data plane: Workers and the inference server. Analytic plane: Record Processors, Records Manager, GPU Telemetry Manager, Server Metrics Manager. A telemetry sidecar streams to OTel and MLflow.
  • Why ZMQ: decoupling orchestration from execution keeps measurement accurate; workers spend their time on I/O and timing. Credits dispatch over ROUTER/DEALER with sticky sessions or least-loaded selection; returns come back on a PUSH/PULL fan-in.
  • README says 10 services; the plugin registry now lists 12 including an optional API service, network-latency probe and a Kubernetes worker-group manager.
  • Lifecycle: initialization → warm-up (discarded) → profiling → collection → processing → aggregation.

  • From docs/cli-options.md. Concurrency (closed loop) issues a new request as soon as one completes; request rate (open loop) sends on a schedule and can be combined with --concurrency as a cap. Arrival patterns: constant, poisson (default), gamma, concurrency_burst; --arrival-smoothness (alias --vllm-burstiness) below 1 is burstier, above 1 smoother.
  • Fixed schedule replays traces at their timestamps (automatic for trace datasets), with --replay-speedup. User-centric timing gives each simulated user a gap of num_users / qps between turns, designed for KV-cache benchmarking.
  • The arrival strip is generated live from each distribution at 5 req/s; it shows shape, not a measurement.






  
Find the limit
Don't guess the operating point. Sweep it, or let AIPerf search for it.

  

    

      

      

        
Method

        
TTFT SLA (ms)600

        

        

      

    

  

  
  • Sweeps: comma lists on --concurrency, --request-rate, --isl and others, grid (default) or zip; YAML sweeps add scenarios plus Sobol / Latin-hypercube sampling (docs/tutorials/sweeps.md).
  • Adaptive search: --search-space, --search-metric, --search-direction, --search-max-iterations; planners bayesian (default; BoTorch, falling back to Optuna TPE), monotonic_sla, smooth_isotonic, optuna. Recipes include max-throughput-ttft-sla, max-concurrency-under-sla and pareto-sweep. Adaptive scale (YAML only) holds load near the edge where an SLA starts failing.
  • The curves are a toy model to show how the two methods probe; dots are probes, not measurements.

Every token is timed. Goodput counts only the requests that met the SLA.

👆 Click any dot to see that request above. Drag the SLOs to move the box.

        

      

    

  

  
  • Top: the selected request, token by token. TTFT is the wait for the first token; ITL is the average gap after it; both are checked against the SLOs. Click any dot below to load that request.
  • Bottom: every request in the run, placed by TTFT and ITL. The green box is the SLO; requests inside it count toward goodput (requests meeting all SLOs / duration, the DistServe definition in docs/metrics-reference.md). Throughput counts all of them.
  • Goodput needs --goodput with metric tags, e.g. "time_to_first_token:600 inter_token_latency:30". Streaming metrics need --streaming.
  • The 60 requests are a toy population to show the idea, not measurements.

Beta in v0.13.0. CRDs: AIPerfJob, AIPerfSweep.

      

      

    

  

  
  • From docs/kubernetes/getting-started.md and the v0.13.0 release notes (beta). The operator chart installs the AIPerfJob and AIPerfSweep CRDs; aiperf kube profile builds an AIPerfJob and the operator creates a JobSet with a controller pod and worker pods. Control-plane services run as sibling containers in the controller pod.
  • Dynamo's own docs recommend benchmarking inside the cluster rather than through a port-forward.
