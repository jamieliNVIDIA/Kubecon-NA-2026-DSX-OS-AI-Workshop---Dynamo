# Super VL TP=2 native Snapshot retest on R610

**Native TP2 capture/restore remains unqualified.** The launch-job prerequisite,
three exact-model runtime preparation variants, and small two-GPU CUDA IPC/NCCL
controls passed. Both compiled native captures were stopped after exceeding a
ten-minute first-rank CUDA checkpoint observation threshold, before CRIU.
After SSH/API access recovered on October 22, the eager capture was also confirmed
failed in first-rank CUDA checkpointing: its source Job exceeded its one-hour
deadline. No native attempt produced a usable artifact or reached restore.
All three runs are now clean: zero active test Pods and zero GPU claims. The
final inventory also found a new contained GPU-error condition on cp-0124,
described below; node readiness and a small CUDA pass do not clear that finding.

Run: `results/20261021-snapshot-tp2-r610/`, namespace
`dynamo-ft-20261022t010526z`. Raw timestamps are UTC (October 22); report date
uses the workstation's October 21 local date.

## R610 source launch integration

R610 alone was insufficient: the common workload image's
`/usr/local/sbin/cuda-checkpoint` is a helper that does not implement
`--launch-job`. The same executable path in the pinned Snapshot agent is the
working driver-facing utility. A fresh owned immutable ConfigMap copies that
verified 5,976-byte ELF executable from agent image
`sha256:973e93dfd2388f3bcba6099de8c4c806262690d23077fd1042b87391bcdd80ff`.
Executable SHA-256: `707fa7f54136824d6c1d6dd724b9b1717610f831033c00d06da474de363a06db`.
The common model image stays unchanged.

`scripts/snapshot-launch-entrypoint.sh` starts the source under `--launch-job`.
`scripts/snapshot-persist-job.sh` copies its transient job file into
`$SNAPSHOT_CONTROL_DIR/cuda-checkpoint-job` before Python initializes CUDA,
then exports that stable path. Restore standby starts `sleep infinity`, leaving
restored CUDA job state to the agent. Each source uses a fresh per-Pod control
volume; the wrapper rejects overwriting an existing job file.

This follows [NVIDIA's R610 job-file contract](https://github.com/NVIDIA/cuda-checkpoint)
and Snapshot 0.1.0's
[source launch wrapper](https://github.com/ai-dynamo/snapshot/blob/v0.1.0/operator/internal/protocol/source_job.go)
and [capture/restore job-file handling](https://github.com/ai-dynamo/snapshot/blob/v0.1.0/agent/internal/cuda/job.go).

### Native attempt 1: default NCCL allocation

The actual capture process inherited the stable job-file path (9,664 bytes at
inspection) and held a DRA claim with devices `gpu-1` and `gpu-3`. Source Pod UID:
`7db7eae5-80ba-466e-8fcc-08248d44e10b`. The model initialized and paused in 55.160s;
the agent began capture at `01:26:25.506934881Z` and resolved both GPU UUIDs.

The agent advanced beyond the previous missing-job-file error, but its first-rank
CUDA checkpoint action stopped showing progress before CRIU. Multiple saved
observations show the same helper command/target, unchanged process I/O and
memory, and only metadata/job-file artifacts. Observed worker memory peak was
204,397,916,160 bytes, below its 256 GiB limit; no OOM events were recorded.
This is not evidence of a storage bottleneck or a usable capture.

The guarded stop recorded a 629-second helper age at `01:36:58Z`, removed only
the owned DGD and capture Job, and allowed normal Pod termination. At
`01:38:06Z`, termination caused the helper to return `CUDA_ERROR_OPERATING_SYSTEM`
after 699.96s; this cleanup-induced error is not the root-cause diagnosis.
At `01:38:32Z`, the run had zero active Pods and zero ResourceClaims. A fresh
two-GPU CUDA/launch bootstrap check on cp-0124 passed at `01:39:15Z`.
Snapshot API objects and local diagnostics are retained; the agent discarded
its incomplete staging directory. No restorable artifact was produced.

To isolate the driver prerequisite, NVIDIA's
[R610 IPC demo](https://github.com/NVIDIA/cuda-checkpoint/blob/00d5cce84c628088d6caa203fc4af40c1538b6f7/src/r610-get-mem-handle-ipc.c)
was adapted to two peers, each with a different GPU. On cp-0198, both processes
verified legacy IPC buffers before and after CUDA checkpoint/restore. The small
control passed on the same common runtime image. It does not perform CRIU or
prove the full vLLM state is supported.

### Native attempt 2: NCCL legacy-allocation control

Separate run: `results/20261021-snapshot-tp2-r610-legacy-ipc/`.
The model revision, image, TP size and storage stay fixed. Only worker NCCL
allocation settings change:

```yaml
NCCL_CUMEM_ENABLE: "0"
NCCL_CUMEM_HOST_ENABLE: "0"
NCCL_NVLS_ENABLE: "0"
```

These [NCCL settings](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/env.html)
disable cuMem device/host allocation and NVLS. CUDA checkpoint's documented
exclusion of `cuMemExportToShareableHandle()` IPC makes this a useful control;
the exact cause of the first attempt's delay is not yet established. The fresh
run has passed cache verification, source bootstrap and client/server dry-runs.
Fresh model preparation also passed: `READY` before/after, 54.934s preparation
and 3.539s restore/wake. Native capture used these settings.

Use `prepare --legacy-ipc --run <fresh-directory>` to reproduce this variant.

The second source reused physical devices `gpu-1` and `gpu-3` on cp-0124.
Inspection of PID 1 and both TP worker environments confirmed all three
overrides. Native capture began at `01:52:58Z` and remained in the first worker's
CUDA checkpoint action, with no CRIU dump started. The guarded stop recorded
640s at `02:03:40Z`; zero active Pods/claims were verified at `02:05:15Z`.
Observed source peak was 203,568,590,848 bytes with zero OOM events. No usable
artifact or restore was produced. These three overrides alone did not fix it.

### CUDA IPC control through the agent helper

`scripts/snapshot_ipc_crossns_control.py` uses the same pinned NVIDIA IPC demo,
modified so the two peers wait while the existing agent's helper performs
lock/checkpoint/restore/unlock through their **host PIDs** and the live job file
under `/host/proc/<container-pid>/root`. Every PID is mapped from the private
container namespace and checked against the owned Pod UID. Each helper call is
bounded at 20 seconds; the owned Pod is removed afterward.

On cp-0124, this passed at `01:55:04Z` using `gpu-4` and `gpu-5`. Both peers
verified their GPU buffers after restoration. The two checkpoint calls completed
in 1.411s and 1.608s including Kubernetes exec overhead. This exercises the
driver/helper/container-boundary path without the full model or CRIU; it does
not establish the cause of the larger vLLM checkpoint stall.

The `--nccl` variant uses `scripts/snapshot_nccl_control_probe.py`: two live
PyTorch NCCL peers all-reduce to 3, park on a CPU event, then all-reduce to 6
after the agent helper restores them. NCCL cuMem/NVLS are disabled and monitoring
settings match Snapshot. This passed on cp-0124 first with `gpu-4`/`gpu-5` at
`02:01:36Z`, and then on the **same `gpu-1`/`gpu-3` pair as both failed model
captures** at `02:07:08Z`. All calls were bounded, and each control Pod was
removed. This rules out a simple GPU-pair or ordinary two-rank NCCL checkpoint
failure in these controls; it still does not qualify the full vLLM engine.

### Eager-mode control

Run: `results/20261021-snapshot-tp2-r610-eager/`. This adds `--enforce-eager`
to the legacy-allocation configuration, removing CUDA graph execution from the
model configuration. Kernel JIT warmup can still occur. Model, image, TP size
and storage are unchanged. Cache, launch bootstrap and effective manifest
dry-runs passed. Fresh eager-mode preparation returned `READY` before/after,
with 67.736s preparation and 3.211s restore/wake. Native eager capture began at
`02:15:57Z`. The last successful API reads before the outage, at `02:20:02Z`, showed capture
in progress, with no usable artifact or restore observed. Saved agent samples
show the first-rank CUDA checkpoint helper waiting and unchanged I/O/memory;
no CRIU dump or artifact data writing had begun.

The local tunnel later disappeared, and reconnecting to `3.238.63.5:22` timed
out. The attempted guarded stop could not read the DGD and made no cluster
cleanup change. The source Job's `activeDeadlineSeconds: 3600` subsequently
expired at `03:07:50Z`. Recovered SnapshotJob status reports `DeadlineExceeded`;
the agent log at `03:08:50.282Z` records the first-rank helper returning
`CUDA_ERROR_OPERATING_SYSTEM` after **3,171.972 seconds**. This error coincides
with source termination and does not identify the cause of the preceding stall.
PodSnapshot reports `Ready=False` and `Failed=True`; no restored worker exists.

Read-only access probes are saved by `scripts/snapshot_access_probe.py`. The
recorded `07:18:02 UTC October 22` probe timed out both directly to the jump
host and to the existing Gemini relay. No cluster mutation occurred during
these probes. Successful API reads resumed on October 22 at `16:27:01 UTC`;
the existing progress, diagnostics and verifier scripts saved the terminal failure. The
agent had no remaining CUDA checkpoint helper. Disabling torch.compile/CUDA
graphs did not resolve the observed stall in this model/runtime configuration.

Reproduce with `prepare --legacy-ipc --eager --run <fresh-directory>` followed
by the same workflow actions above.

## Interpretation and remaining work

The driver upgrade and source wrapper resolved the missing launch-job gate.
The small controls demonstrate working two-GPU legacy IPC and ordinary NCCL
checkpoint/restore through the agent helper, including the exact GPU pair used
by the full model. They do not cover all resources held by the full vLLM engine.

The observed model captures wait inside the first TP worker's CUDA checkpoint
call. CRIU and artifact data writing have not started, so these observations
do not implicate EFS restore bandwidth or demonstrate that changing artifact
storage would fix this failure. No further cluster infrastructure change has
been identified by these tests.

The exact remaining CUDA/vLLM/library resource is not isolated. The repeated
pre-capture Xid timeline makes source preparation the next isolation target,
using a small vLLM/FlashInfer workspace control or a runtime with
matching validated multi-GPU checkpoint integration. Upstream's
[multi-GPU snapshot discussion](https://github.com/vllm-project/vllm/issues/52125)
describes communicator, CUDA IPC, symmetric-memory/custom-all-reduce and graph
state as separate boundaries; this is context, not proof of this run's cause.

The observed worker memory peaks above are **pre-CRIU observations from failed
captures**, not end-to-end minimum memory requirements. No new restore timing
or complete artifact size is available from these attempts.
